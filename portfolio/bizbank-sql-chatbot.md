# SQL Chatbot — 금융 업무 의미를 반영한 SQL 조회

**비즈앤뱅크 인턴십 · Dify, SQLGlot, SAP HANA**

“이번달 지급내역 보여줘”라고 물었을 때 급여 지급 정의가 선택되면, SQL이 정상 실행돼도 사용자가 찾던 지급 실행 내역과 다른 결과가 나옵니다. 해외 펌뱅킹 챗봇에서 저는 질문을 올바른 업무 정의에 연결하고, 생성된 SQL의 실행 전 검사와 SAP 금액 조회 규칙을 개선했습니다. 회사 구현 코드와 실행 기록은 비공개입니다.

## 지급 실행 의도를 업무 카드에 연결

v6.4에서 지급 실행 질문에 본문이 긴 급여 지급 카드가 반복해서 매칭되는 문제를 발견했습니다. 누락을 피하려고 여러 후보를 함께 넘기면 관계없는 업무 정의도 SQL 생성 문맥에 들어갔습니다. v6.6에서는 예시 질문과 별칭을 자식 청크로 검색하고, 매칭된 부모 업무 카드에서 조회에 필요한 테이블·컬럼과 규칙을 가져왔습니다. 점수가 `0.45` 미만이거나 1위와 `0.02`를 초과해 차이 나는 카드는 제외했습니다.

지급 질의 35턴으로 검색을 평가해 첫 질문 20건의 업무 카드 Top-1 적중이 **12/20 → 19/20**으로 높아진 것을 확인했습니다. 35턴 전체에서 1·2위 점수가 `0.03` 기준으로 근접한 경우는 **19건 → 12건**으로 줄었습니다. 두 지표는 검색이 어떤 업무 카드를 골랐는지 평가한 결과입니다.

## SAP 원시값을 조회 금액으로 보정

당시 조회한 SAP `CURR` 필드에서는 소수 자릿수가 0인 원화 금액의 원시값이 실제 금액의 **1/100**이었습니다. 그대로 합산하면 결과가 100배 작아졌습니다. 원화로 저장된 금액을 원화로 조회할 때도 SAP HANA의 `CONVERT_CURRENCY`를 거친 뒤 합산하도록 규칙을 바꿨습니다. 같은 통화에 변환을 적용해 저장 자릿수를 보정했고, 내부 실행에서 원시값 **535.3 → 원화 53,530**을 확인했습니다.

## 실행 전 검사와 실패 응답

v6.4 해외 Dify 워크플로에서는 SQLGlot으로 생성 SQL의 AST를 분석해 조회 문장이 하나인지, `SELECT` 구조와 허용 테이블·컬럼을 따르는지 검사했습니다. 허용 범위는 검증 노드에 전달한 업무 정의에서 가져왔습니다. Dify에서 실행 전 검사를 수행하고, 실제 조회는 Java API를 거쳐 SAP에서 실행하는 흐름으로 구분했습니다.

업무 의도를 확정하기 어려우면 SQL 실행 전에 조건을 되물었습니다. 재시도는 SQL 생성·검증 단계로 제한해 타임아웃이 난 SAP 조회를 자동 반복하지 않도록 했습니다. 유효한 SQL을 만들지 못해 검증 재시도 한도를 넘긴 경우와 SAP 조회가 타임아웃된 경우는 응답 실패로 처리했습니다. 정상 실행이 0행을 반환하면 조회된 행이 없다고 안내했습니다.
