# [Biznbank SQL Chatbot] Payment Intent Matching and SAP Currency Scaling

**금융 업무 인턴십 · 지급 질의 검색과 실행 전 검증 개선 · Dify, SQLGlot, SAP HANA** | *(사내 보안 정책상 원본 코드 비공개)*

> ### 📌 Context & Constraints
>
> - **Objective** 해외펌뱅킹 담당자가 자연어로 지급 내역과 금액을 조회할 수 있도록 챗봇을 개발했습니다.
> - **Problem** ‘지급’은 실제 지급 실행, 급여 지급, 승인 상태 등 여러 업무를 가리킵니다. 업무 의도를 잘못 해석하면 SQL이 정상 실행돼도 다른 내역이나 금액이 반환됐습니다.
> - **Constraints** 조회 비용과 응답 시간을 줄이면서 그룹통화 집계와 SAP 금액 자릿수 규칙을 지켜야 했습니다. SAP 조회 실패와 정상 조회의 0행 결과도 사용자에게 다르게 안내해야 했습니다.
> - **Scope** 지급 질의의 업무 카드 검색, 질문 해석과 SQL 생성 단계의 모델 설정, SAP 금액 조회 규칙, 실행 전 SQL 검증을 개선했습니다.

## Decisions & Troubleshooting

### 1. 지급 실행 카드 검색

v6.4에서는 “이번달 지급내역 보여줘”처럼 지급 실행을 묻는 질의에도 텍스트가 긴 급여 지급 카드가 반복해서 매칭됐습니다. 정답 후보를 남기기 위해 여러 카드를 함께 전달하는 방식은 관련도가 낮은 정보까지 SQL 생성 프롬프트에 넣어 입력을 키웠습니다.

v6.6에서는 업무 카드에서 DB 상세 정의를 가져오기 전에 부모·자식 청크 검색을 적용했습니다. 예시 질문과 별칭을 자식 청크로 검색하고, 매칭된 청크의 부모 업무 카드에서 SQL 생성에 필요한 정의를 가져왔습니다. 검색 점수가 `0.45` 미만이거나 1위와의 점수 차가 `0.02`를 초과하는 카드는 제외했습니다. *(사내 지급 질의 35턴 검색 평가로 검증했으며, 업무 카드와 평가셋이 포함된 원본은 비공개입니다.)*

### 2. 질문 해석과 SQL 생성 모델 선택

질문 재구성과 분류를 별도로 호출하던 흐름을 줄이기 위해 두 작업을 `gemini-3.5-flash-lite`의 질문 해석 호출 한 번으로 합쳤습니다. SQL 생성 노드 두 곳까지 `gemini-3.5-flash-lite`로 바꾸면 비용은 줄었지만, 그룹통화 기준으로 합산해야 할 금액을 원화로 묶는 등 결과의 업무 의미가 달라졌습니다.

경량 모델은 질문 해석에 적용하고, SQL 생성에는 `gemini-3.7-flash`를 유지했습니다. SQL 생성의 `thinking_level`은 `Low`로 낮췄고, 모델이 만드는 한글 머리글은 계산 컬럼에만 허용했습니다. *(사내 동일 31턴 모델 비교의 실행 결과와 비용 기록을 사용했으며, 금융 조회 질의와 생성 SQL이 포함된 원본은 비공개입니다.)*

### 3. SAP 통화 자릿수 보정

“지급금액 원화로 알려줘”라는 질의에서 당시 조회한 SAP `CURR` 필드는 원화처럼 소수 자릿수가 0인 통화도 실제 금액의 **1/100**로 저장했습니다. 원시값을 그대로 합산하면 실제 금액보다 100배 작은 값이 답변에 나왔습니다.

원화에서 원화로 조회하는 경우에도 `CONVERT_CURRENCY`를 거친 뒤 금액을 합산하도록 지급 규칙을 바꿨습니다. 동일 통화에 변환을 적용한 목적은 SAP 저장 자릿수를 보정하는 것이었습니다. *(사내 SAP HANA 실행에서 원시값과 변환값을 대조했으며, 지급 데이터와 조회 SQL 원본은 비공개입니다.)*

### 4. SQL 검증과 응답 처리

SQL이 실행되더라도 허용된 조회 범위를 벗어나거나 질문에 필요한 업무 조건이 빠질 수 있었습니다. SAP 조회 자체를 자동으로 재시도하면 무거운 조회를 반복해 대기 시간이 늘 수 있어, SQL 검증 단계에서 재시도 범위를 제한했습니다.

SQLGlot으로 생성 SQL을 파싱해 조회 문장이 하나인지, 조회에 제공한 테이블과 컬럼을 사용하는지 검사했습니다. 질문의 의미를 확정하기 어려우면 SQL을 실행하기 전에 필요한 조건을 되물었습니다. 검증 재시도 한도를 넘거나 SAP 조회가 타임아웃되면 응답 실패로 종료했고, 정상 실행 결과가 0행이면 조회한 행이 없다고 안내했습니다. *(사내 워크플로의 SQLGlot 검증 코드와 응답 분기 로직을 근거로 했으며, 회사 구현 코드는 비공개입니다.)*

## Validation & Results

**업무 카드 검색.** 첫 질문 20건에서 Top-1 적중이 **12/20 → 19/20**으로 높아졌습니다. 35턴 검색 평가에서 1·2위 점수가 `0.03` 기준으로 근접한 경우는 **19건 → 12건**으로 줄었습니다. *(사내 검색 비교 평가의 질문·정답 카드와 점수 기록은 비공개입니다.)*

**SQL 생성 모델 비교.** `temperature=0`, `thinking_level=Low`를 비롯한 나머지 설정을 고정한 동일 31턴에서 SQL 생성 노드 두 곳을 경량 모델로 바꾸자 비용은 **$0.579 → $0.329**로 줄었고, 재시도는 **0 → 9턴**, 실행 오류는 **0 → 5턴**으로 늘었습니다. *(사내 모델 비교 로그에는 금융 조회 질의와 생성 SQL이 포함돼 있어 비공개입니다.)*

**SAP 금액 보정.** 동일 통화 변환을 적용한 내부 실행에서 원시값 **535.3 → 원화 53,530**을 확인했습니다. *(사내 SAP HANA 실행의 원시값·변환값 대조 기록이며, 업무 데이터가 포함돼 비공개입니다.)*

**v6.4와 v6.6 비교.** 10월 1일 v6.4와 10월 6일 v6.6에서 개인 급여 거부 문항을 제외하고 공통 질문 번호 26개를 다시 집계했습니다. 평균 응답 시간은 **19.9초 → 12.0초**, 질문당 비용은 **$0.0338 → $0.0203**, 총 토큰은 **952,333 → 643,630**, 총 비용은 **$0.87849 → $0.52782**였습니다. 이 비교에는 질문에 입력한 식별자가 달라진 두 건과 개선본에서 날짜 변환 오류가 발생한 한 건이 포함됐습니다. 해당 세 건을 제외한 23문항에서도 평균 응답 시간은 **18.57초 → 12.03초**였습니다. *(사내 원본 실행 로그를 공통 질문 번호로 대조했습니다. 조회 식별자와 실행 결과가 담긴 로그는 비공개입니다.)*

**v6.6 원본과 1612본 비교.** 같은 GCMS 초안 **15개 대화**에서 질문당 카드 수는 **3.00 → 1.43장**, SQL 생성 프롬프트는 **31.7K → 20.4K 토큰**, SQL 생성 출력은 **1,355 → 384토큰**이었습니다. 질문 해석 단계의 중앙값은 **2.77초 → 1.45초**, 질문 한 건의 보고 응답 시간은 **15.3초 → 10.3초**였습니다. 총 토큰은 **454K → 288K**, 총 비용은 **$0.411 → $0.231**이었고, 판정은 두 버전 모두 통과·실패·보류 **6/0/9**였습니다.

SQL 생성의 프롬프트 입력은 약 **11.3K토큰**, 출력은 **971토큰** 감소했습니다. 입력 감소에는 검색 카드 축소와 프롬프트 재배치가, 출력 감소에는 `thinking_level` 변경과 머리글 축소가 함께 반영됐습니다. 라우터 단계의 시간 차이는 중앙값 **1.32초**였습니다. 총 비용 절감 **$0.180**을 역산하면 약 **$0.142**는 토큰 수 감소분이고, 약 **$0.038**은 입력·출력 구성과 모델 단가가 함께 반영된 실효 비용 변화분이었습니다. *(사내 GCMS 초안 15개 대화의 비교 기록을 사용했습니다. 질의별 실행 내역과 판정 자료는 비공개입니다.)*
