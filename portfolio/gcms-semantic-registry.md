# GCMS Registry — SAP 스키마를 업무 조회 규칙으로 연결

**비즈앤뱅크 인턴십 · SAP GUI·ADT, ABAP DDIC, Python, Dify**

컬럼명이 비슷해도 업무에서 가리키는 단계가 다르면 조회 대상과 집계 결과가 달라집니다. 해외 펌뱅킹 챗봇을 만들면서 저는 SAP 원천 정의와 업무 규칙을 대조하고, 검토용 문서와 챗봇이 사용하는 조회 정의를 같은 원본에서 생성했습니다. SAP 스키마와 사내 업무 자료는 비공개입니다.

## 컬럼명만으로 내린 업무 판단을 정정

테이블과 컬럼 이름으로 분류한 업무 영역을 검토하다 `DRAFTSTATUS`의 `draft`가 전자결재 기안으로 잘못 분류된 사례를 발견했습니다. SAP GUI의 테이블 설명과 DDIC 도메인 값을 대조해 중국 법인 어음의 상태임을 확인했고 관련 테이블 **18개**의 분류를 바로잡았습니다. 이후에는 리포트 프로그램의 실제 사용 조건을 살피고, 해석이 필요한 항목은 현업 담당자에게 확인했습니다.

지급 오류를 조회하는 질의를 검증하면서 생성 SQL이 지급 송신 상태와 은행 파일 응답 상태를 `OR`로 묶는 것을 발견했습니다. 그대로 실행하면 송신에 실패한 건과 은행이 파일을 받은 뒤 응답한 건이 같이 조회될 수 있었습니다. 지급 송신 오류에는 송신 상태 `SENDST = 'N'`을 쓰고 기간은 송신 상태 일자 `SENDSTDT`에 적용하도록 정의했습니다. 은행의 응답 상태 `FACKST`는 파일 응답 단계에 해당합니다. 업무 정의를 바꾼 뒤 레지스트리와 카드별 조회 문맥을 다시 생성해 송신 오류 규칙이 반영됐는지 확인했습니다.

## 업무 카드에서 필요한 조회 정의 조립

처음에는 DDL을 직접 색인했습니다. ‘매출’이나 ‘순매출’처럼 스키마에 없는 표현은 관련 없는 테이블에 매칭됐고, 테이블을 개별 검색하면 조인에 필요한 관계가 빠졌습니다. 전체 스키마를 붙이면 입력 토큰이 커졌습니다.

업무 카드의 이름·설명·별칭·예시 질문을 검색하고, 선택한 카드에서 참조하는 테이블·컬럼·조인·업무 규칙을 조립해 SQL 생성에 전달했습니다. 업무 정의는 Markdown에 두고 Python으로 현업 검토용 엑셀과 실행용 레지스트리 JSON·검색 자료를 생성했습니다. 현업 검토에서 규칙을 고치면 같은 정의에서 조회 문맥을 다시 만들 수 있었습니다.

## 금액과 통화, 흐름과 잔액의 집계 규칙

금액을 합산하려면 어떤 통화인지 알아야 하며, 기간 중 발생한 금액과 특정 시점의 잔액에는 서로 다른 집계 기준이 필요했습니다. v6.8에서는 SAP ADT로 가져온 DDIC의 `@Semantics.amount.currencyCode`에서 금액·통화 컬럼의 연결을 추출하고, ABAP 리포트의 `DO_SUM`·`COLLECT`와 확인된 업무 규칙을 참고해 집계할 측정값을 정의했습니다. 흐름과 시점 잔액을 구분한 규칙을 JSON으로 생성해 Dify의 SQL 검증과 차트·분석 코드에서 참조하도록 연결했습니다.

## 확인한 범위

- 8월 4주 발표에서 **질의 두 건**으로 전체 스키마를 전달하는 방식과 필요한 업무 정의만 전달하는 방식을 비교했습니다. 두 질의 모두 기대한 SQL을 생성했고, 필요한 정의만 전달했을 때 토큰 사용량은 각각 **6,200 → 2,700**, **7,000 → 3,800**으로 줄었습니다.
- 9월에는 SAP CBO 테이블 **140개**를 분류하고, **4,553개 중 3,935개(86.4%)** 컬럼의 의미를 업무 사전에 매핑했습니다.
- 생성한 **레지스트리 234건**을 구조 검사해 오류·경고가 모두 **0건**임을 확인했습니다. v6.8 집계 정의에서는 측정 컬럼 후보 **75개 중 74개**에 통화 참조가 연결된 것을 확인했습니다. 업무 규칙은 앞의 분류·조회 사례에서 SAP 원천과 대조했습니다.
