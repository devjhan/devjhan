# [Windows Deployment Kit] Validating Artifacts Before Service Replacement

**비즈앤뱅크 인턴십 · 배포·서비스 교체·롤백 자동화 · PowerShell 7, Windows Batch, NSSM, Spring Boot, React** | *(사내 보안 정책상 원본 코드 비공개)*

> ### 📌 Context & Constraints
>
> - **Objective** 사내 Windows 서버에 Spring Boot·React 애플리케이션을 배포하는 절차를 자동화했습니다.
> - **Problem** 개발자가 원격으로 접속해 JAR를 교체하고 서비스를 재시작했습니다. React 빌드가 빠져도 Spring Boot의 JAR 빌드가 성공할 수 있었습니다.
> - **Constraints** 공장 내 외부 도구 반입이 제한됐고, 일부 서버에는 JRE만 제공됐습니다. 펌뱅킹의 거래 정합성을 고려해 서비스 교체 시 프로세스가 겹치는 상황도 피해야 했습니다.
> - **Scope** Jenkins나 GitHub Actions 같은 별도 CI/CD 플랫폼을 도입하기 어려운 환경에서 사내 NAS의 Git 저장소와 NSSM을 활용했습니다. `deploy.bat` 한 번으로 소스 동기화, 빌드, 산출물 검사, 서비스 교체와 헬스 체크를 실행하는 PowerShell 키트를 만들었습니다. 빌드 호스트에는 JDK 17과 Node.js를 준비하도록 구성했습니다.

## Decisions & Troubleshooting

### 1. 서비스 정지 전 빌드 산출물 검사

React 빌드를 빠뜨려도 Spring Boot의 `bootJar`가 성공해 화면에 필요한 파일이 빠진 JAR가 만들어질 수 있었습니다. 빌드 명령의 종료 코드만 확인하고 교체를 시작하면 정적 파일이 누락된 상태로 배포할 위험이 있었습니다.

프런트엔드와 백엔드의 빌드 순서를 `project.json`에 명시하고, 각 단계의 종료 코드와 `expect`에 지정한 산출물을 확인했습니다. React 빌드 뒤에는 `dist/index.html`을, 최종 JAR 내부에서는 `jarContains`로 `BOOT-INF/classes/static/index.html`을 검사했습니다. 빌드나 패키징에서 문제가 생기면 기존 서비스를 정지하기 전에 배포를 중단했습니다. *(사내 배포 스크립트의 검사 로직과 데모 설정을 근거로 했으며, 서버 구성과 프로젝트 설정이 포함된 원본은 비공개입니다.)*

### 2. 운영 설정 외부화와 재시작 명령 분리

포트 같은 운영 설정을 JAR 내부에 두면 값 하나를 수정할 때도 빌드와 배포를 반복해야 했습니다. NSSM 서비스가 시작할 때 외부 `config/application.yml`을 읽도록 하고, `restart.bat`을 배포 명령과 분리했습니다.

운영 설정을 수정한 뒤 같은 JAR로 서비스를 재시작해 변경을 반영할 수 있었습니다. 포트를 바꿀 때는 헬스 체크도 같은 포트를 사용하도록 `project.json`의 값을 맞췄습니다. *(사내 NSSM 등록 설정과 재시작 스크립트를 근거로 했으며, 운영 환경 설정 원본은 비공개입니다.)*

### 3. 동시 배포 차단과 서비스 정지 확인

펌뱅킹에서는 처리 중인 요청을 강제로 끊거나 두 프로세스가 겹쳐 뜨면 거래 정합성에 영향을 줄 수 있었습니다. 배포 시작 시 프로젝트 디렉터리에 배타적 파일 잠금을 잡아 같은 애플리케이션의 배포가 겹치는 것을 막았습니다.

기존 JAR와 버전 정보를 보관하고, NSSM 서비스가 `Stopped` 상태에 도달한 뒤에만 교체했습니다. 별도 재시작 명령은 같은 JAR을 사용하는 Java 프로세스가 남아 있으면 중단했습니다. *(사내 배포·재시작 스크립트의 파일 잠금, 서비스 상태, 잔존 프로세스 검사 로직을 근거로 했으며, 서비스 관리 코드 원본은 비공개입니다.)*

### 4. 기동·헬스 체크 실패 시 이전 버전 복구

교체 후에는 새 버전이 기동하고 헬스 체크에서 HTTP 200을 반환해야 배포가 성공했다고 판단했습니다. 기동 또는 헬스 체크가 실패하면 이전 JAR와 버전 정보를 복원하고, 서비스를 다시 시작해 헬스를 확인하도록 구현했습니다.

복구에 성공하면 종료 코드 `2`를 반환했습니다. 복구 대상이 없거나 복원 후에도 기동·헬스 확인이 실패하면 종료 코드 `3`을 반환하고, 운영자 개입이 필요한 이유를 로그에 남겼습니다. *(사내 롤백 구현과 종료 코드 정의를 근거로 했으며, 서비스 운영 절차가 포함된 원본은 비공개입니다.)*
