# Windows Deployment Kit — 서비스 정지 전 배포 산출물 검증

**비즈앤뱅크 인턴십 · PowerShell 7, Windows Batch, NSSM, Spring Boot, React**

개발자가 Windows 서버에 원격 접속해 JAR를 교체하고 서비스를 재시작했습니다. React 빌드가 빠져도 Spring Boot JAR 빌드는 성공할 수 있어, 빌드 성공 여부만으로는 교체 전에 화면 파일 누락을 탐지하기 어려웠습니다. 공장 내 외부 도구 반입이 제한되고 일부 서버에는 JRE만 제공돼 별도 CI/CD 플랫폼을 도입하기 어려웠습니다. 저는 사내 NAS의 Git 저장소와 NSSM을 이용해 배포를 제어하는 PowerShell 키트를 구현했습니다. 서비스 설정과 사내 소스는 비공개입니다.

## 교체 전에 빌드 결과 검사

`deploy.bat`으로 소스를 동기화하고 프런트엔드와 백엔드를 순서대로 빌드하도록 했습니다. 빌드 호스트에는 JDK 17과 Node.js가 필요했습니다. `project.json`에 빌드 단계와 검사할 산출물을 지정하고, 각 명령의 종료 코드도 검사했습니다. React 빌드 뒤에는 `expect`로 `dist/index.html`을, 패키징 뒤에는 `jarContains`로 최종 JAR의 `BOOT-INF/classes/static/index.html`을 확인했습니다. 빌드나 검사에서 실패하면 서비스 정지 단계 전에 종료했습니다.

## 서비스 교체와 재시작 제어

포트처럼 운영 중 조정하는 값은 외부 `config/application.yml`에 두었습니다. NSSM 서비스가 이 파일을 읽도록 했고, `restart.bat`을 별도로 제공해 같은 JAR로 설정 변경을 반영할 수 있었습니다. 포트를 바꿀 때는 `project.json`의 헬스 체크 포트도 맞췄습니다.

같은 애플리케이션의 배포가 겹치지 않도록 프로젝트 디렉터리에 배타적 파일 잠금을 잡았습니다. 기존 JAR와 버전 정보를 보관했습니다. 배포에서는 NSSM 서비스가 `Stopped`에 도달한 뒤 파일을 교체했고, 별도 재시작 명령은 같은 JAR를 실행하는 Java 프로세스가 남아 있으면 중단하도록 구현했습니다.

## 새 버전 기동 실패 후 복구

새 버전은 기동 후 헬스 체크에서 HTTP 200을 반환해야 배포 성공으로 처리했습니다. 기동이나 헬스 확인이 실패하면 이전 JAR와 버전 정보를 복원하고, 서비스를 다시 시작해 헬스를 확인하도록 구현했습니다. 복구를 완료하면 종료 코드 `2`를 반환했습니다. 복구 대상이 없거나 복구 후에도 기동·헬스 확인에 실패하면 종료 코드 `3`과 운영자 개입 사유를 남겼습니다.
